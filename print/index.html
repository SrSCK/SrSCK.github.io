Try it

What it is

A student chats by text or voice with an AI patient, or a parent of a child patient, across 17 clinical cases. At the end the student gets a summary and an AI-graded score, and instructors review sessions in an admin dashboard.

Where it started

The previous team had already deployed the system, but it was not reliable in real use because the AI patient sometimes made things up. A student cannot learn diagnosis from a patient who denies the very symptom that points to it. My first audit found ten gaps, including sessions that lived only in memory, no check at all on what the model said, weak authentication and a dead API key. The raw API error, including a fragment of the key, was even showing up inside the patient's chat bubble.

What I built

Output validator (my main AI contribution). After the patient model replies, a second, cheap model call checks the reply against the case's real clinical facts before the student sees it. It runs at temperature 0 with JSON output and flags four failure types.

Failure type Meaning Real example caught
Contradiction denies or states something that conflicts with the case a mother denied leg swelling that the case documents
Invention adds a clinical detail the case never mentions "child looked lethargic" when the case says the child is playing well
Leak states the diagnosis the student should work out
Implausible behaviour that is wrong for the patient's age a 9-month-old who "tries to drink water" by themself

A flagged reply is regenerated with a correction hint, up to two times. If the judge call itself fails, the reply passes through, so a broken check never blocks a student. In exam mode the validator is always on.

Results, stated honestly. Across about 50 hand-checked replies over 6 cases it made 8 confirmed catches, 1 confirmed miss and 1 borderline call. On a real 12-turn run it caught 2 hallucinations, including the patient denying a sore throat, which is the key clue for post-streptococcal glomerulonephritis in that case. It cost about 19 percent more tokens (39,674 versus 33,431).

Session scoring. An LLM judge grades the whole interview from 0 to 100 against the case ground truth. It judges the process (did the student's questions surface the key facts) rather than only the final diagnosis, and returns what was covered and what was missed. If the judge fails, the score is left empty instead of faking a zero.

Reliability. Sessions were lost whenever the server restarted, so I saved a snapshot of the conversation state after every turn and restored it on demand. I verified it with a real kill-and-restart. I also stopped raw errors from reaching students by logging them on the server and showing a safe Thai message instead.

Security. The admin SQL editor ran raw SQL as a database superuser. I replaced it with an allowlist plus a read-only transaction. My first two attempts at read-only mode did nothing because of autocommit, and I only found out by trying a real UPDATE against the database. The third attempt worked.

Persona fix. Asked about swollen lymph nodes in her child, the AI "mother" replied "I came because my child is sick". The cause was a vague persona rule whose example phrase had become a catch-all. I rewrote it into three cases (questions about the parent, questions about the child, and genuinely unrelated questions) and re-tested it live.

Speech pipeline. Speech to text through Groq Whisper with re-encoding of browser recordings to WAV, a local Thai text-to-speech fallback, a medical vocabulary list in the transcription prompt, and a small rule in code that stops the correction step from flipping the speaker's gender particle (ครับ or ค่ะ).

Model bake-off. With no funded API key, I tested 10 free models through a proxy. Only GPT-4.1-mini produced correct, in-persona Thai, so it stayed as the development model.

Deployment. Frontend on Vercel, backend on Render, database on Supabase, with sign-in, admin and Thai chat verified on the deployed site.

In total I made 71 commits and 14 pull requests, adding about 7,200 lines and removing about 3,000.

Honest limits

  • The validator results come from a small sample checked by one reviewer, and the same model both generated and judged the replies.
  • In one case the generator only softened an error after two retries instead of fixing it.
  • The session score has not been compared with instructor grades.
  • Full production use needs a funded API key and stronger authentication.

What I took away

Put checks around the model instead of hoping a better prompt will hold. Enforce hard requirements in code. And a checker that shares the generator's model and view of the case tends to fail in the same places. That last observation became the research question I want to study in graduate school.

My Agent Operating Setup

The way I build almost everything, with several AI coding agents working under shared rules, shared memory and a habit of verification.

Try it

Why I built it

Agents are fast but forgetful and overconfident. I wanted them to behave like teammates who follow written rules, leave proper handoffs and prove their work before calling it done.

How it works

Shared rules. One global rule file applies to every project. It routes work by difficulty (small models for mechanical tasks, mid-size models for normal work, the largest models for architecture and high-risk changes), and each task announces which tier it uses and why. I audited my agent definitions against this table and moved several to a better-fitting tier.

Required habits. Default skills make every agent debug systematically, verify before reporting a task as complete, and brainstorm and stress-test plans before building.

Shared memory. Every project has a control-center note in my Obsidian vault with a section written for the next agent, the commands that are verified to work, the current status, durable decisions and the next step. Agents update it when they finish a task, so a new session, or a different agent, can pick up the work without me repeating myself.

Clear boundaries. When two agents work on related things, the notes say who owns what. In Money Printer, Claude and Codex run separate tracks and never share credentials or publishing state.

Knowledge library. A library folder collects what I have studied with AI help, including small retrieval corpora that agents can query. The retrieval part is still in progress.

Token hygiene. A command-line proxy filters long shell output before it reaches the agent, which keeps sessions cheaper and more focused.

Honest limits

  • This setup is tuned for one person. It has not been tested with a team.
  • I use AI to write a lot of my code, so some parts I understand at the level of design and behaviour rather than every line. Learning those internals properly is one of my goals.

What I took away

Most agent failures I see are not about intelligence. They come from missing context, unclear ownership or nobody checking the result. Writing those things down fixes more problems than switching models.

Money Printer

An agent pipeline that writes, voices, edits, schedules and analyses a YouTube channel of history Shorts, posting twice a day without manual editing.

Try it

What it does

Each day an agent writes short scripts about true stories from history into a queue. The pipeline voices each script with a local text-to-speech model, finds public-domain footage on Archive.org (passed through a vision check and a blank-clip check) and public-domain photos from Wikimedia, applies a colour grade, normalises loudness to -14 LUFS, renders the Short and schedules two uploads a day at times chosen for a US evening audience. Separate analyst agents then pull channel data every day and write reports on traffic sources, audience, first-two-day views and retention.

Decisions that matter

  • Everything runs on free tools and public-domain media only.
  • No automated engagement comments, because they look like a bot.
  • New formats need my explicit approval before anything is published.
  • Any new automation must fail closed if it cannot verify which channel it is about to post to.
  • The Claude track and the Codex track (a separate vertical-drama workflow for a channel that does not exist yet) never share credentials, schedules or analytics.

Where it stands

The channel is small and not monetised. After a format change, first-two-day views dropped sharply, and I recorded the cause as unproven rather than guessing. A 16:9 long-form pilot (8.4 minutes, five stories) has been rendered but not published.

Honest limits

  • Growth is slow and the cause of the recent drop is not yet known.
  • The YouTube login token expires every 7 days until the app's consent screen is moved to production.

What I took away

Running a pipeline that posts for real teaches different lessons from a demo. The hard parts were failure handling, scheduling and knowing when the data is too thin to draw a conclusion.

teambrain

A shared cloud workspace where a small team and all of its AI agents keep project notes and agent history in one place, with a live feed of what every agent is doing.

Problem
Teams that use several agents (Claude Code, Codex, Cursor, Hermes) end up with context scattered across tools.
Built
An MCP server over streamable HTTP with three tools (list projects, pull context, push context), workspace tokens stored only as SHA-256 hashes, and a rate limit of 60 requests per minute per token.
Found
While testing, I found that the server connected to the database as the table owner, which silently bypassed the row-level security I had written.
Role
Solo founder and developer
Context
Personal, planned as a six-week test build starting 28 August 2026
Stack
Next.js 16 (App Router), Supabase (Postgres, Auth, Storage, Realtime), Drizzle ORM, Tailwind CSS, shadcn/ui, Model Context Protocol (MCP) TypeScript SDK, Vercel
Status
Prototype. Weeks 1 to 6 of the test build are done and deployed. The product is not finished.

Try it

The idea

Teams that use several agents (Claude Code, Codex, Cursor, Hermes) end up with context scattered across tools. teambrain keeps each project's linked notes and agent history in the cloud. Any MCP-capable agent can pull project context and write back what it did, and teammates, technical or not, watch it live in a browser. Code stays on each person's machine.

What I built

  • A data model of eight tables (workspace, member, project, note, link, attachment, activity, invite) with row-level security policies on every table.
  • An MCP server over streamable HTTP with three tools (list projects, pull context, push context), workspace tokens stored only as SHA-256 hashes, and a rate limit of 60 requests per minute per token. I verified it connected to Claude Code.
  • A live, workspace-wide agent activity feed as the signature feature, grouped by actor with colour-coded avatars and per-action icons.
  • Write modes for agent edits, with pending badges so people can see what still needs approval.
  • Notes with wiki-style links and autocomplete, magic-link sign-in and file attachments.

A decision I made on purpose

Context retrieval is two steps in version one. The agent first sees note titles, then picks what to read. I left embeddings and hybrid search for a later version to keep the six-week build small and predictable.

A security finding

While testing, I found that the server connected to the database as the table owner, which silently bypassed the row-level security I had written. The real guard was the app's own data-access layer. I documented this rule for every future query, and in a later fix made the browser's database roles read-only.

Honest limits

  • It is a test build, not a finished product, and it has no paying users.
  • Email invitations only reach the owner's address until a domain is verified.
  • Some keyboard interactions in the editor could only be verified by unit tests, not by automated browser tests.

What I took away

The interesting problem is not storing notes. It is letting several agents share one memory without stepping on each other, and making their work visible enough that people can trust it.

HSK Learning App

A web app I built to teach myself Chinese, covering the HSK 1 to 4 syllabus with spaced repetition, stroke-order practice and quizzes that are hard to guess.

Built
The app follows a 39-week plan through 339 lessons covering 2,026 words and 339 grammar points, with meanings and grammar explanations in Thai.
Tested
Database security rules have automated tests that run on a local emulator, never against production.
Lesson
A quiz that is easy to game measures nothing.
Role
Sole builder and main user
Context
Personal, 2026
Stack
Vanilla JavaScript, Firebase (Auth, Firestore, Hosting), HanziWriter, browser Web Speech API
Status
Live

Try it

What it does

The app follows a 39-week plan through 339 lessons covering 2,026 words and 339 grammar points, with meanings and grammar explanations in Thai. Lessons unlock step by step. Each word has pinyin, a Thai meaning, an example sentence, audio and stroke-order practice in watch and quiz modes. A spaced-repetition scheduler decides what to review, and a library page collects every word from lessons I have passed.

Details I care about

  • Quiz distractors are chosen to be similar to the right answer, by meaning category for meaning questions and by sound for pinyin and listening questions, so I cannot pass by guessing.
  • The word list was cross-checked against the official HSK database, and when duplicates turned up I removed them instead of inventing replacement words.
  • Database security rules have automated tests that run on a local emulator, never against production.

Honest limits

  • Audio depends on the user's operating system having a Chinese voice installed.
  • It uses Simplified characters, while Taiwan uses Traditional characters, so my next step is to add Traditional forms.

What I took away

Building the tool made me a more disciplined learner, and the same principle as my other work applies. A quiz that is easy to game measures nothing.
