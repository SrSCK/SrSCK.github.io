What it is

A student chats by text or voice with an AI patient, or a parent of a child patient, across 17 clinical cases. At the end the student gets a summary and an AI-graded score, and instructors review sessions in an admin dashboard.

Where it started

The previous team had already deployed the system, but it was not reliable in real use because the AI patient sometimes made things up. A student cannot learn diagnosis from a patient who denies the very symptom that points to it. My first audit found ten gaps, including sessions that lived only in memory, no check at all on what the model said, weak authentication and a dead API key. The raw API error, including a fragment of the key, was even showing up inside the patient's chat bubble.

What I built

Output validator (my main AI contribution). After the patient model replies, a second, cheap model call checks the reply against the case's real clinical facts before the student sees it. It runs at temperature 0 with JSON output and flags four failure types.

Failure type Meaning Real example caught
Contradiction denies or states something that conflicts with the case a mother denied leg swelling that the case documents
Invention adds a clinical detail the case never mentions "child looked lethargic" when the case says the child is playing well
Leak states the diagnosis the student should work out
Implausible behaviour that is wrong for the patient's age a 9-month-old who "tries to drink water" by themself

A flagged reply is regenerated with a correction hint, up to two times. If the judge call itself fails, the reply passes through, so a broken check never blocks a student. In exam mode the validator is always on.

Results, stated honestly. Across about 50 hand-checked replies over 6 cases it made 8 confirmed catches, 1 confirmed miss and 1 borderline call. On a real 12-turn run it caught 2 hallucinations, including the patient denying a sore throat, which is the key clue for post-streptococcal glomerulonephritis in that case. It cost about 19 percent more tokens (39,674 versus 33,431).

Session scoring. An LLM judge grades the whole interview from 0 to 100 against the case ground truth. It judges the process (did the student's questions surface the key facts) rather than only the final diagnosis, and returns what was covered and what was missed. If the judge fails, the score is left empty instead of faking a zero.

Reliability. Sessions were lost whenever the server restarted, so I saved a snapshot of the conversation state after every turn and restored it on demand. I verified it with a real kill-and-restart. I also stopped raw errors from reaching students by logging them on the server and showing a safe Thai message instead.

Security. The admin SQL editor ran raw SQL as a database superuser. I replaced it with an allowlist plus a read-only transaction. My first two attempts at read-only mode did nothing because of autocommit, and I only found out by trying a real UPDATE against the database. The third attempt worked.

Persona fix. Asked about swollen lymph nodes in her child, the AI "mother" replied "I came because my child is sick". The cause was a vague persona rule whose example phrase had become a catch-all. I rewrote it into three cases (questions about the parent, questions about the child, and genuinely unrelated questions) and re-tested it live.

Speech pipeline. Speech to text through Groq Whisper with re-encoding of browser recordings to WAV, a local Thai text-to-speech fallback, a medical vocabulary list in the transcription prompt, and a small rule in code that stops the correction step from flipping the speaker's gender particle (ครับ or ค่ะ).

Model bake-off. With no funded API key, I tested 10 free models through a proxy. Only GPT-4.1-mini produced correct, in-persona Thai, so it stayed as the development model.

Deployment. Frontend on Vercel, backend on Render, database on Supabase, with sign-in, admin and Thai chat verified on the deployed site.

In total I made 71 commits and 14 pull requests, adding about 7,200 lines and removing about 3,000.

Honest limits

  • The validator results come from a small sample checked by one reviewer, and the same model both generated and judged the replies.
  • In one case the generator only softened an error after two retries instead of fixing it.
  • The session score has not been compared with instructor grades.
  • Full production use needs a funded API key and stronger authentication.

What I took away

Put checks around the model instead of hoping a better prompt will hold. Enforce hard requirements in code. And a checker that shares the generator's model and view of the case tends to fail in the same places. That last observation became the research question I want to study in graduate school.
